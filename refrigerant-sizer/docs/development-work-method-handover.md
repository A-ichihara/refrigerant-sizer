# 開発作業の進め方・判断基準 引き継ぎ書

- 対象プロジェクト：冷媒選定アプリ開発
- 用途：ChatGPT（チャッピー）が採用している作業方法・判断基準を、Antigravityなど別の担当者へ共有する
- この文書の対象外：個別機能の仕様、配管径の数値、具体的な不具合一覧などの技術内容そのもの
- 基本方針：**小さく切り分けて一つずつ解決し、根拠と検証結果を確認してから次へ進む**

## 1. 作業の基本姿勢

### 1.1 大きな変更を急がず、確認可能な単位に分ける
一度に多くの箇所を変更するより、問題を小さな作業単位に分解する。各単位について「何を確認・変更するのか」「何をもって完了とするのか」を明確にしてから着手する。

例：
1. 現状のコードと既存のテストを読む
2. 問題の発生条件と影響範囲を絞る
3. 最小限の変更を行う
4. 変更に対応するテストを追加・更新する
5. テスト実行結果と差分を確認する
6. 変更をコミットし、次の課題へ進む

複数の小さな作業をまとめて進める場合も、内部ではこの確認単位を保ち、無関係な変更を混ぜない。

### 1.2 「動くこと」より「正しいと確認できること」を重視する
画面に結果が表示されること、計算が完了すること、テストが通ることは、それぞれ別の事実である。特に技術計算・設計支援では、表示された値が正しい根拠を持つかを別途確認する。

根拠が不足している場合は、推測で完成扱いにせず、未確認であることを明示する。必要なら警告・制限・安全停止を維持する。

### 1.3 不確実な問題を無理に解決済みにしない
情報不足のまま仮定を積み上げて実装しない。確認できていること、可能性にとどまること、未確認のことを区別する。正しい判断に必要な資料がない場合は、調査課題として残し、根拠のない変更を避ける。

## 2. 調査・修正の進め方

### 2.1 変更前に現状を確認する
- 対象ファイルと関連処理を読む
- 呼び出し元・呼び出し先やUIとのつながりを確認する
- 既存テスト、既存の警告、制約条件を確認する
- 過去の変更や直近のCI結果があれば確認する
- 既に解決済みの問題を再度変更しないよう、現状のコミットを確認する

コードの一部だけを見て、全体の動作を決めつけない。

### 2.2 原因と対策を分ける
症状を見つけた段階で即座に修正するのではなく、再現条件・原因候補・影響範囲を整理する。修正は、確認できた原因に対して最小限に行う。原因が特定できない場合は、推測を事実のように扱わない。

### 2.3 安全側の制約を不用意に外さない
未検証の処理に対する警告、入力範囲チェック、危険な操作の無効化などは、作業を進めるうえで邪魔に見えても、根拠なしに削除しない。解除する場合は、解除条件・根拠・影響・回帰テストを明確にする。

### 2.4 変更範囲を限定する
- 1コミットにつき、原則として一つの目的を持たせる
- 関係のない整形やリファクタリングを同時に混ぜない
- 既存機能への影響がありそうな箇所はテストで確認する
- 変更理由が説明できない差分を残さない

## 3. テストと検証の考え方

### 3.1 変更内容に対応するテストを用意する
単に既存テストを通すだけでなく、今回の修正で守りたい条件をテストにする。通常ケースだけでなく、該当する場合は境界値、未対応入力、不正値、既存動作への非影響も確認する。

### 3.2 テストの種類を混同しない
以下は別々に扱う。
- **コードを変更した**：差分が作られた
- **テストを追加した**：確認手段を用意した
- **ローカルでテストが通った**：指定環境でテストが成功した
- **CIが成功した**：GitHub Actions等の該当ワークフローが成功した
- **実機・実運用で確認した**：対象環境での動作を確認した
- **仕様上正しいと確認した**：信頼できる仕様・公式資料等との照合が済んだ

一つの段階を、別の段階の完了として報告しない。CIが未実行・実行中なら、そのまま明記する。

### 3.3 テストが通っても仕様の正しさを自動的に保証しない
テストは、書かれた期待値と条件に対して動作するかを確認するもの。期待値自体が正しいかは別問題である。技術的な基準値・設計条件については、信頼できる資料と照合する。

### 3.4 失敗時は原因を切り分ける
テスト失敗時に、根拠なくテストを削除したり期待値を変更したりして通すことを避ける。失敗が実装の不具合なのか、テストの誤りなのか、環境の問題なのかを調べ、修正後に再確認する。

## 4. 根拠と判断の優先順位

判断に使う情報は、一般に次の順で重視する。

1. 対象機種・対象バージョンに一致するメーカー公式資料、正式仕様
2. プロジェクト内で確認済みの仕様・要件・受け入れ条件
3. 再現可能なテスト結果や、実際のコード・実行結果
4. 信頼できる補助資料
5. 推測・経験則・類似機種からの類推

上位の根拠と矛盾する場合、下位の情報だけで仕様を決めない。資料の対象範囲・発行時期・機種・適用条件も確認する。資料の表や図が十分に読み取れない場合は、読み取れたことにして数値を確定しない。

## 5. GitHubでの変更管理

1. 変更前に対象ファイルの最新内容とSHAを取得する
2. 差分の目的を一つに絞って編集する
3. 対応するテストを追加・更新する
4. 変更差分と、既存の重要な条件が残っていることを確認する
5. 明確なメッセージでコミットする
6. GitHub Actionsの該当ワークフローを確認する
7. コミットとCIの結果を記録し、次の作業へ進む

コミットが作成されたことだけで、作業全体が成功したとは判断しない。CIの結果が確認できない場合は「未確認」とする。別の担当者が引き継ぐ際は、作業ツリーや最新コミットを改めて確認し、過去の会話だけを最新状態とみなさない。

## 6. 作業の優先順位

基本的には次の順で扱う。

1. 誤った結果・危険な誤用につながる問題
2. 入力チェック、対応範囲、エラー処理などの安全性
3. 既存機能を壊す回帰不具合
4. 仕様・公式根拠の不足と検証手段の整備
5. 操作性、表示、説明文などの改善
6. 見た目だけの微調整や、緊急性の低い整理

ただし、見た目の修正であっても誤解や誤使用を招く場合は、優先順位を上げる。

## 7. ユーザーへの報告方法

### 7.1 毎回の進捗率報告はしない
ユーザーから継続指示があった場合、短い合図のたびに進捗率や同じ説明を繰り返さない。意味のある変更、検証の完了、重要な判断、ブロッカーの発見など、共有価値がある節目で報告する。

### 7.2 報告は事実・結果・残課題に分ける
報告には必要に応じて以下を含める。
- 何を変更・確認したか
- どのテストを実施し、結果がどうだったか
- コミット等の参照先
- まだ確認できていないこと
- 次に何を確認するか

未実行の作業を実行済みのように説明しない。また、メッセージを受け取った後にバックグラウンドで作業が継続していると誤認させない。実際にツールで実行・確認できた作業だけを報告する。

### 7.3 承認を求める条件
通常の小さな修正やテスト追加は、既定の作業方針に沿って進める。一方、費用が発生するサービスの利用、重大な設計方針の変更、データの破壊的操作、既存の安全制約の解除などは、必要に応じて事前に説明して承認を得る。

## 8. 作業の完了条件

一つの作業を「完了」とする前に、可能な範囲で以下を確認する。

- [ ] 問題・目的・対象範囲が明確
- [ ] 変更内容が目的に必要な範囲に限定されている
- [ ] 変更に対応するテストがある、またはテストできない理由が記録されている
- [ ] 関連テストの実行結果を確認した
- [ ] 既存の安全制約や重要な警告が不用意に失われていない
- [ ] 公式仕様など、外部根拠が必要な点を照合した／未照合として明記した
- [ ] 差分・コミットを確認した
- [ ] CI結果を確認した／未確認として明記した
- [ ] 残課題と次の一手が説明できる

すべての項目を満たせない場合でも、作業自体を止める必要があるとは限らない。ただし、未完了の項目を隠さず、作業の状態を正確に引き継ぐ。

## 9. 別担当者へ引き継ぐときの注意

- まず最新ブランチ、最新コミット、変更差分、CI状況を確認する
- この文書は「作業方法」の共有であり、個別機能の仕様書の代わりにはしない
- 技術的な数値・機種適用範囲・設計基準は、別途、対象に合う根拠資料を確認する
- 既存の警告や安全停止は、解除根拠が確認できるまで維持する
- 既に確認済みのことを再調査する場合も、過去の記録と現在の状態が一致するか確認する
- 大きな変更を急ぐより、小さな変更・検証・記録を積み重ねる
- 不確かなことは不確かと明記し、次の担当者が判断を誤らないようにする

## 10. 最も大切にする考え方

**「一つずつ潰す」とは、細かい作業を増やすこと自体が目的ではない。変更の影響と検証結果を追跡可能にし、誤りを早い段階で見つけ、未確認事項を完成扱いしないための方法である。**

スピードだけでなく、根拠・再現性・安全性・引き継ぎやすさを両立させる。確認できた事実を積み上げ、未確認の部分は明確に残しながら前進する。
