# 冷媒配管サイズ選定システム 修正・検証 作業手順書

更新日: 2026-10-20  
対象リポジトリ: https://github.com/A-ichihara/refrigerant-sizer  
対象ブランチ: `main`

## 1. 目的

冷媒配管サイズ選定システムについて、既存機能を不用意に壊さず、メーカー公式の設計・施工資料に基づいて不具合を調査・修正し、テスト結果と未解決事項を記録する。見た目やコードの整形よりも、配管径・配管長・分岐部材・部材数量が設計根拠に適合することを優先する。

本アプリの計算結果は、対象型式・シリーズの最新公式資料との照合を完了するまでは、メーカー承認済みの設計値として扱わない。

## 2. 作業の基本原則

1. **公式資料を先に確認する。** 閾値、境界条件、管種、対象区間、冷媒、シリーズ、型式、容量比率を推測で補わない。
2. **既存動作を先に記録する。** 修正前の再現手順、入力ツリー、計算結果、警告、BOMを記録してから変更する。
3. **小さく変更する。** 無関係なリファクタリングや大規模なUI変更を同時に行わない。
4. **計算値と表示値・BOMを一体で検証する。** 画面の管径表示だけ変わり、配管長や材料集計が変わらない修正を合格としない。
5. **不明な場合は未対応として明示する。** 根拠の不足を「一般的な仕様」や他シリーズの資料で埋めない。
6. **費用を発生させない。** 有料資料・有料アプリ・課金サービス等が必要になった場合は、利用前にユーザーの承認を得る。
7. **大きな仕様変更は事前確認する。** データ構造の大規模変更、既存UIの広範な変更、利用者データへの影響がある変更は、実施前に概要と影響を説明して承認を得る。通常の調査、局所的な修正、テスト、文書化は事前承認を求めず進める。
8. **GitHub上の実行結果を区別する。** ローカル相当の直接実行、構文チェック、Node.jsテスト、GitHub Actionsは別々に記録し、未実行のものを成功と報告しない。

## 3. 対象と優先順位

### 3.1 先行して対応する不具合・リスク

- Carrier: FSユニットのシリーズ判定誤警告、再帰集計・構文に関する回帰確認。
- GHP 4社（アイシン、ダイキン、ヤンマー、パナソニック）: 主管サイズアップ処理が室外機ノードだけに反映され、実際の配管区間やBOMに反映されない可能性。
- Panasonic EHP: UXE3系統の電磁弁キット上流3管式／下流2管式の区間処理、および長配管時自動サイズアップの適用条件。
- 各エンジンの配管長、容量比率、分岐継手、配管径、警告、BOMの相互整合性。

### 3.2 作業順序

1. リポジトリ・対象ファイル・現行テスト・CIの状態を確認する。
2. メーカー別・シリーズ別に公式資料とアプリ内の型式・冷媒・配管方式を照合する。
3. 再現可能な最小テストを作り、修正前の挙動を固定する。
4. データモデルと配管区間の意味を整理する。
5. 公式条件が確認できた範囲のみ、最小変更で修正する。
6. 単体・回帰・境界値・集計テストを追加する。
7. GitHub Actionsを実行し、結果を確認する。
8. 差分とテスト結果を再確認し、変更内容・制約・残課題を文書化する。
9. 作業報告書を作成し、変更コミットと根拠資料へのリンクをまとめる。

## 4. 公式資料の確認手順

対象メーカー・シリーズごとに、以下を確認して記録する。

- 資料名、版・発行年月、公式URL、該当ページ・図表。
- 対象型式、シリーズ世代、冷媒、2管式／3管式、冷暖切換／冷暖同時。
- 室外機容量、室内機接続容量・接続台数、容量比率条件。
- 配管長の定義（実長／相当長）、最遠配管長、主管長、分岐後の許容長。
- 増径の閾値（「以上」か「超える」かを含む）、増径対象の管種、対象区間、増径量。
- 分岐部材・継手の相当長、径別の配管表、異径継手の要否。
- 資料間で条件が異なる場合の適用範囲と、未解決の差異。

別シリーズ・別冷媒・旧世代資料の条件を、根拠なく現行アプリ全体に適用しない。

## 5. 配管ツリーと集計の確認手順

現行データモデルでは、通常、各子ノードの `length` は親ノードから当該ノードまでの配管区間長を表す。実装・検証では次を確認する。

1. ノードの機器種別と、親子関係がメーカー配管図に対応しているか。
2. 配管区間の管種と管径が、その区間の長さ・BOMへ反映されるか。
3. 分岐後の枝管容量が、枝管径選定に正しく用いられるか。
4. 3管式の各管（液管・吐出ガス管・吸入ガス管）と、電磁弁キット等の下流2管式が正しい区間に集計されるか。
5. 主管と枝管で管径が異なる場合、区間分割と異径継手を表現できるか。
6. 実長と相当長を区別し、継手相当長を計算していない場合に実長を相当長として表示しないか。
7. 同じ区間やノードが再帰処理により二重集計されないか。
8. 無効な長さ（負数、NaN、Infinity）、重複ID、循環・ノード再利用等を安全に拒否または警告するか。

現在のUIで表現できない機器・区間は、実在すると推測して自動分類せず、未対応として記録する。

## 6. 実装手順

1. 変更前の対象ファイルSHA、関連テスト、現在の挙動を記録する。
2. 変更する条件を、公式資料の該当箇所と1対1で対応づける。
3. まずテストで既知の誤動作を再現する。
4. 必要最小限のコード変更を行う。
5. 計算結果、ノードの管径表示、警告、BOM、総配管長を比較する。
6. 関連する他シリーズで副作用がないことを回帰テストで確認する。
7. コメント・設計メモに、適用範囲と根拠を記録する。
8. 変更を小さなコミットに分け、何を直したかをコミットメッセージに明記する。

公式条件が確定していない場合、誤った管径を確定出力する実装は行わず、未照合警告・監査メモ・テストを先に整備する。

## 7. 必須テスト項目

対象に応じて以下を実施する。

- 構文チェック（engine、UI）。
- エンジン初期化と主要関数の存在確認。
- 正常系：2管式、3管式、複数分岐、単一室内機、複数室内機。
- 境界値：公式閾値の直前・一致・直後。「以上」「超える」の区別を含む。
- 容量比率・室内機台数の境界値。
- 管径の段階選定、増径上限、未定義サイズの処理。
- 配管区間ごとの長さ、管種別総長、総長の整合性。
- 分岐継手・電磁弁キット等の型番・数量・適用位置。
- 手動サイズアップと自動サイズアップの重複適用。
- エラー入力・未対応構成・不正なツリーの安全な処理。
- 表示・印刷・出力の警告や注意事項の欠落がないこと。
- 既存機能の回帰テストとGitHub Actions。

合格報告では、テスト名、実行方法、件数、結果、未実施項目を明記する。「構文が通る」「代表例が通る」を「メーカー仕様に完全適合」と言い換えない。

## 8. 完了判定

修正対象ごとに、以下を満たしたときに完了とする。

- 公式資料と対象シリーズの適用範囲が明確である。
- 修正前の不具合がテストで再現され、修正後に解消される。
- 配管径表示、区間長、BOM、警告が一貫している。
- 関連する既存テストと回帰テストが成功している。
- GitHub Actionsの結果を確認している（未実行・取得不能なら、その旨を明記）。
- 変更差分とコミットを確認している。
- 残課題、適用範囲、手動で確認すべき事項を記録している。

資料不足やモデル表現の不足が残る場合は「部分完了」または「未実装」とし、完了扱いにしない。

## 9. 作業報告書の様式

各作業単位で次を報告する。

1. **対象・目的**
2. **確認した公式資料**（URL、版、該当箇所、適用範囲）
3. **修正前の問題と再現条件**
4. **変更ファイルと変更内容**
5. **テスト結果**（方法・件数・成功／失敗）
6. **GitHub Actions**（実行URLと結果、または未確認の理由）
7. **設計上の制約・未解決事項**
8. **コミットリンク**
9. **次の作業**
